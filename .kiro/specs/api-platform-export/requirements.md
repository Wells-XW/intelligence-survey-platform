# Requirements Document

## Introduction

T15 ("API Open Platform and Export Enhancement") extends the Intelligence Survey Platform with a public integration surface and an enriched data export pipeline. The feature delivers four tightly coupled capabilities: (1) auto-published REST API documentation derived from FastAPI's OpenAPI schema, (2) user-managed API keys with scoped permissions and rotation, (3) webhook subscriptions with HMAC-signed delivery and retry semantics, (4) multi-format asynchronous data export covering CSV, Excel, JSON, SPSS, and SAS. Cross-cutting concerns include per-key rate limiting backed by Redis, append-only audit logging that aligns with the existing T10 compliance module, and strict reuse of the existing JWT/RBAC permission model so that an API key never grants more access than its owning user already has.

This feature is delivered as backend FastAPI endpoints, Celery worker tasks, and a small set of admin pages embedded in the existing main React application. It explicitly excludes OAuth 2.0/SSO, GraphQL, gRPC, and a separately deployed developer portal; those remain candidates for a later release.

## Glossary

- **Survey_Platform**: The Intelligence Survey Platform backend (FastAPI service) that owns survey, response, distribution, and compliance domains.
- **API_Key**: A long-lived bearer credential issued to a registered user; consists of a public identifier prefix and a secret portion that is shown once at creation and stored only as a hash thereafter.
- **API_Key_Service**: The Survey_Platform subsystem responsible for the lifecycle of API keys (create, list, rotate, revoke, validate).
- **Scope**: A capability label of the form `<resource>:<action>` (for example `survey:read`, `response:write`) attached to an API_Key and checked on each request.
- **Owner_User**: The registered platform user that created an API_Key; the API_Key inherits the Owner_User's RBAC permissions on individual surveys.
- **API_Documentation_Service**: The component that publishes the OpenAPI specification, the rendered Swagger UI, the rendered ReDoc page, and the curated usage guide.
- **Webhook_Subscription**: A configuration record bound to a survey or to the Owner_User account that lists one or more event types and a target HTTPS URL.
- **Webhook_Event**: A discrete domain event that may trigger webhook delivery; the initial set is `response.created`, `response.completed`, `quota.reached`, and `distribution.sent`.
- **Webhook_Delivery_Worker**: The Celery worker that consumes webhook delivery jobs from Redis and performs the outbound HTTP POST with retry.
- **HMAC_Signature**: An HMAC-SHA256 signature of the raw webhook request body, computed with a per-subscription signing secret and transmitted in the `X-Webhook-Signature` HTTP header.
- **Export_Job**: An asynchronous unit of work that materializes survey response data into a downloadable file in a requested format.
- **Export_Format**: One of `csv`, `xlsx`, `json`, `sav`, `sas7bdat`. `csv` and `xlsx` and `json` are required; `sav` and `sas7bdat` are best-effort and depend on `pyreadstat` availability at runtime.
- **Export_Worker**: The Celery worker that executes Export_Jobs and writes the resulting file to project storage.
- **Rate_Limiter**: The Redis-backed component that counts and rejects API requests that exceed configured per-API_Key quotas.
- **Audit_Log**: The append-only persistence surface defined by the existing T10 `audit.py` model; new event types added by this feature are written to the same table.
- **Compliance_Module**: The T10 ethics and compliance subsystem that this feature integrates with for audit alignment with PIPL and GDPR obligations.

## Requirements

### Requirement 1: Public REST API Documentation

**User Story:** As an external developer integrating with a survey owner's data, I want browsable API documentation with usage guides and code samples, so that I can authenticate and call endpoints without reading source code.

#### Acceptance Criteria

1. THE API_Documentation_Service SHALL publish the OpenAPI 3.x JSON schema generated by FastAPI at the path `/api/v1/openapi.json`.
2. THE API_Documentation_Service SHALL render an interactive Swagger UI at the path `/api/v1/docs`.
3. THE API_Documentation_Service SHALL render an alternative ReDoc view at the path `/api/v1/redoc`.
4. THE API_Documentation_Service SHALL annotate every public endpoint in the OpenAPI schema with a summary, a description, and at least one example request payload and one example response payload.
5. THE API_Documentation_Service SHALL document both authentication paths (JWT bearer and API_Key) in the OpenAPI security schemes section.
6. THE API_Documentation_Service SHALL publish a usage guide accessible from the documentation page that includes code samples for authentication, listing surveys, fetching responses, registering a Webhook_Subscription, and starting an Export_Job, in at least two languages from the set {Python, JavaScript, cURL}.
7. WHEN a non-public internal endpoint is registered with the FastAPI router, THE API_Documentation_Service SHALL exclude that endpoint from the published OpenAPI schema.

### Requirement 2: API Key Lifecycle Management

**User Story:** As a survey owner integrating the platform with an external system, I want to create, rotate, and revoke API keys with named scopes and optional expirations, so that I can grant least-privilege access and respond to credential incidents without disrupting other integrations.

#### Acceptance Criteria

1. WHEN an authenticated Owner_User submits a key creation request that includes a name, a non-empty scope list, and an optional expiration timestamp, THE API_Key_Service SHALL create a new API_Key, persist its hashed secret, and return the plaintext secret in the response body exactly once.
2. WHILE a created API_Key has not yet been revoked or expired, THE API_Key_Service SHALL accept it as a valid credential on requests that present it in the `Authorization: Bearer <key>` header or in the `X-API-Key` header.
3. THE API_Key_Service SHALL store every API_Key secret only as a salted hash and SHALL NOT return the plaintext secret on any endpoint other than the original creation response.
4. WHEN an Owner_User requests rotation of an existing API_Key, THE API_Key_Service SHALL generate a new secret for that key, invalidate the previous secret immediately, and return the new plaintext secret exactly once.
5. WHEN an Owner_User requests revocation of an existing API_Key, THE API_Key_Service SHALL mark the key as revoked and SHALL reject all subsequent requests presenting that key with HTTP status 401.
6. IF an incoming request presents an API_Key whose stored expiration timestamp is in the past, THEN THE API_Key_Service SHALL reject the request with HTTP status 401 and a machine-readable error code `api_key_expired`.
7. WHEN authorizing a request authenticated by an API_Key, THE Survey_Platform SHALL grant access only to the intersection of (a) the scopes attached to the API_Key and (b) the RBAC permissions of the Owner_User on the target survey.
8. WHEN an Owner_User lists their API_Keys, THE API_Key_Service SHALL return for each key its identifier, name, scope list, creation timestamp, expiration timestamp, last-used timestamp, and revocation status, but SHALL NOT include the plaintext secret or its hash.
9. WHERE an API_Key has gone unused for a configurable inactivity threshold, THE API_Key_Service SHALL flag the key as inactive in list responses to support hygiene review.

### Requirement 3: Webhook Subscription Configuration

**User Story:** As a survey owner integrating with a downstream CRM, I want to subscribe to platform events on a target URL with a per-subscription signing secret, so that my downstream system can react to survey activity in near real time and verify that callbacks are genuine.

#### Acceptance Criteria

1. WHEN an authenticated Owner_User submits a Webhook_Subscription create request that contains an HTTPS target URL, a non-empty event type list drawn from the supported Webhook_Event set, and an optional description, THE Survey_Platform SHALL create the subscription, generate a fresh signing secret, and return the signing secret in the response body exactly once.
2. IF a Webhook_Subscription create or update request specifies a target URL whose scheme is not `https`, THEN THE Survey_Platform SHALL reject the request with HTTP status 400 and a machine-readable error code `webhook_url_must_be_https`.
3. IF a Webhook_Subscription create or update request specifies an event type that is not in the supported Webhook_Event set, THEN THE Survey_Platform SHALL reject the request with HTTP status 400 and a machine-readable error code `webhook_event_unsupported`.
4. WHEN an Owner_User requests rotation of a Webhook_Subscription signing secret, THE Survey_Platform SHALL generate a new secret, attempt to invalidate the previous secret, and return the new secret exactly once.
5. IF invalidation of the previous signing secret fails after a new secret has been generated, THEN THE Survey_Platform SHALL accept both secrets as valid for HMAC verification and SHALL retry invalidation in the background until it succeeds.
6. WHEN an Owner_User requests deletion of a Webhook_Subscription, THE Survey_Platform SHALL stop dispatching new deliveries for that subscription and SHALL retain its delivery history for the configured audit retention period.
7. WHEN an Owner_User lists their Webhook_Subscriptions, THE Survey_Platform SHALL return for each subscription its identifier, target URL, event type list, creation timestamp, last delivery status, and active flag, but SHALL NOT include the signing secret.

### Requirement 4: Webhook Event Delivery and Retry

**User Story:** As an integrator, I want webhook deliveries to be reliable in the face of transient downstream failures, so that my system is not silently desynchronized when my receiver is temporarily unavailable.

#### Acceptance Criteria

1. WHEN a Webhook_Event matching at least one active Webhook_Subscription is emitted by the Survey_Platform, THE Webhook_Delivery_Worker SHALL enqueue one delivery job per matching subscription.
2. WHEN executing a delivery job, THE Webhook_Delivery_Worker SHALL perform an HTTPS POST to the subscription's target URL with the event payload as a JSON body and SHALL include the headers `Content-Type: application/json`, `X-Webhook-Event` set to the event type, `X-Webhook-Delivery` set to a unique delivery identifier, and `X-Webhook-Signature` set to the HMAC_Signature of the raw request body.
3. THE Webhook_Delivery_Worker SHALL compute the HMAC_Signature using HMAC-SHA256 keyed by the subscription's current signing secret over the exact byte sequence of the request body.
4. WHEN a delivery attempt actually receives a complete HTTP response from the target URL with a status code in the range 200 through 299 inclusive, THE Webhook_Delivery_Worker SHALL mark the delivery as successful and SHALL NOT retry.
5. IF a delivery attempt fails with a network error, a timeout greater than 10 seconds, or an HTTP response status code outside 200 through 299, THEN THE Webhook_Delivery_Worker SHALL schedule a retry using exponential backoff with at least the schedule {1 minute, 5 minutes, 30 minutes, 2 hours, 12 hours} for up to 5 attempts total.
6. IF all retry attempts for a delivery have failed, THEN THE Webhook_Delivery_Worker SHALL mark the delivery as permanently failed and SHALL record the final HTTP status code or error reason in the delivery history.
7. IF the retry scheduling mechanism itself fails when attempting to enqueue a retry attempt, THEN THE Webhook_Delivery_Worker SHALL mark the delivery as permanently failed immediately and SHALL record the scheduling failure reason in the delivery history.
8. WHEN a delivery transitions to permanently failed, THE Webhook_Delivery_Worker SHALL emit a `webhook.delivery.failed` audit event referencing the subscription and the delivery identifier.
9. WHEN an Owner_User requests the delivery history for a Webhook_Subscription, THE Survey_Platform SHALL return for each delivery its identifier, event type, attempt count, last attempt timestamp, last response status, and final status.
10. WHERE an Owner_User triggers a manual redelivery of a recorded delivery, THE Webhook_Delivery_Worker SHALL create a new delivery attempt with a new delivery identifier and SHALL preserve the original event payload byte-for-byte.

### Requirement 5: Multi-Format Data Export

**User Story:** As a researcher analyzing survey data in SPSS, I want to export responses to formats my analysis tools accept, so that I can perform statistical work without writing custom converters.

#### Acceptance Criteria

1. WHEN an authenticated Owner_User submits an export request specifying a survey identifier and a target Export_Format from the set {csv, xlsx, json}, THE Survey_Platform SHALL create an Export_Job in status `queued` and SHALL return the job identifier in the response.
2. WHERE the Survey_Platform's runtime environment has the `pyreadstat` library available, THE Survey_Platform SHALL additionally accept Export_Format values `sav` and `sas7bdat`.
3. IF an Owner_User submits an export request with an Export_Format value that is not currently supported by the runtime, THEN THE Survey_Platform SHALL reject the request with HTTP status 400 and a machine-readable error code `export_format_unsupported`.
4. WHEN an Export_Job is dequeued, THE Export_Worker SHALL transition the job to status `running`, materialize the survey responses into the requested Export_Format, write the file to project storage, and transition the job to status `succeeded` with the storage location recorded.
5. THE Export_Worker SHALL produce CSV files encoded in UTF-8 with a byte-order mark and with a header row that lists the question identifiers in the survey's canonical question order.
6. THE Export_Worker SHALL produce XLSX files containing one row per response and one column per question, with a header row matching the CSV header layout.
7. THE Export_Worker SHALL produce JSON files containing a top-level array whose elements are response objects keyed by question identifier.
8. WHERE the requested Export_Format is `sav` or `sas7bdat`, THE Export_Worker SHALL embed the survey's question text as variable labels and SHALL embed defined choice options as value labels.
9. IF an Export_Job fails during materialization, THEN THE Export_Worker SHALL transition the job to status `failed`, record a non-empty error message, and SHALL NOT retain a partial output file.
10. WHEN an Owner_User requests the status of an Export_Job, THE Survey_Platform SHALL return the job identifier, status, requested format, creation timestamp, completion timestamp if any, error message if any, and a download URL if and only if the status is `succeeded`.
11. WHILE an Export_Job is in status `succeeded`, THE Survey_Platform SHALL serve the resulting file via a time-limited download URL that requires authentication of the Owner_User or of an API_Key whose scopes include `export:read`.
12. WHEN the configured retention period for a completed Export_Job elapses, THE Survey_Platform SHALL delete the materialized file from storage and SHALL transition the job's status to `expired`.

### Requirement 6: Per-API-Key Rate Limiting

**User Story:** As a platform administrator, I want every API key to have enforced request quotas, so that one integration cannot exhaust shared resources or cause noisy-neighbor incidents for other tenants.

#### Acceptance Criteria

1. WHEN a request authenticated by an API_Key is received, THE Rate_Limiter SHALL increment the per-API_Key counters for the current minute, hour, and day windows in Redis before forwarding the request to the route handler.
2. IF the per-API_Key request count for the current minute, hour, or day window exceeds the configured quota for that window, THEN THE Rate_Limiter SHALL reject the request with HTTP status 429 and SHALL NOT invoke the route handler.
3. WHEN the Rate_Limiter rejects a request with HTTP status 429, THE Rate_Limiter SHALL include in the response a `Retry-After` header whose value is the integer number of seconds until the most restrictive exceeded window resets.
4. THE Rate_Limiter SHALL include in every successful response the headers `X-RateLimit-Limit` set to the active per-minute quota, `X-RateLimit-Remaining` set to the remaining minute-window allowance, and `X-RateLimit-Reset` set to the Unix timestamp at which the minute window resets.
5. THE Rate_Limiter SHALL apply the platform's default per-minute, per-hour, and per-day quotas to any API_Key that does not have an explicit override configured.
6. WHERE an administrator has configured a per-API_Key quota override, THE Rate_Limiter SHALL apply the override values in place of the platform defaults for that API_Key.
7. IF the Redis backing store is unavailable when the Rate_Limiter attempts to read or increment a counter, THEN THE Rate_Limiter SHALL fail closed by rejecting the request with HTTP status 503 and SHALL emit a `rate_limiter.backend_unavailable` audit event.

### Requirement 7: Audit Trail for API, Webhook, and Export Activity

**User Story:** As a platform administrator responsible for PIPL and GDPR alignment, I want every credential lifecycle change, webhook delivery, and export job recorded in an append-only audit log, so that I can produce evidence of who accessed what data and when during a compliance review.

#### Acceptance Criteria

1. WHEN an API_Key is created, rotated, or revoked, THE Survey_Platform SHALL append an Audit_Log entry that records the actor user identifier, the API_Key identifier, the action verb, and the timestamp.
2. WHEN a Webhook_Subscription is created, updated, has its signing secret rotated, or is deleted, THE Survey_Platform SHALL append an Audit_Log entry that records the actor user identifier, the subscription identifier, the action verb, and the timestamp.
3. WHEN a Webhook_Delivery_Worker completes a delivery attempt with a final outcome of either succeeded or permanently failed, THE Survey_Platform SHALL append an Audit_Log entry that records the subscription identifier, the delivery identifier, the event type, the final outcome, and the timestamp.
4. WHEN an Export_Job transitions to status `succeeded`, `failed`, or `expired`, THE Survey_Platform SHALL append an Audit_Log entry that records the actor user identifier, the survey identifier, the Export_Format, the job identifier, the terminal status, and the timestamp.
5. WHEN a request authenticated by an API_Key is rejected with HTTP status 429 by the Rate_Limiter, THE Survey_Platform SHALL append an Audit_Log entry that records the API_Key identifier, the request method, the request path, the exceeded window label, and the timestamp.
6. THE Audit_Log SHALL be append-only and SHALL NOT expose any API endpoint that mutates or deletes existing entries.
7. WHEN a platform administrator with the `audit:read` scope queries the Audit_Log, THE Survey_Platform SHALL return matching entries filtered by any combination of actor user identifier, API_Key identifier, subscription identifier, time range, and event type.
8. THE Audit_Log entries created by this feature SHALL conform to the schema of the existing T10 `audit.py` model so that the Compliance_Module can include them in its existing PIPL and GDPR exports.
9. IF a new audit event carries fields that do not fit any column of the existing T10 `audit.py` schema, THEN THE Survey_Platform SHALL persist only the schema-compatible fields and SHALL accept that the unmappable fields are not retained.

### Requirement 8: Authentication Coexistence and RBAC Inheritance

**User Story:** As a survey owner who already uses the platform UI with JWT login, I want API keys to act as an alternative authentication path that respects the same RBAC roles, so that I never accidentally grant broader access through a key than the user who created it already has.

#### Acceptance Criteria

1. WHEN an incoming request presents both a JWT access token and an API_Key, THE Survey_Platform SHALL authenticate the request using the JWT and SHALL ignore the API_Key for that request.
2. WHEN an incoming request presents a valid API_Key and no JWT, THE Survey_Platform SHALL authenticate the request as the Owner_User of the API_Key.
3. IF an incoming request presents neither a valid JWT nor a valid API_Key on an endpoint that requires authentication, THEN THE Survey_Platform SHALL reject the request with HTTP status 401.
4. WHEN authorizing a request authenticated by an API_Key against a survey-scoped endpoint, THE Survey_Platform SHALL evaluate the Owner_User's RBAC role on the target survey and SHALL deny the request with HTTP status 403 if that role does not permit the operation.
5. THE Survey_Platform SHALL NOT issue, refresh, or extend JWT tokens through any API_Key-authenticated endpoint.
6. WHEN an Owner_User's account is disabled, THE Survey_Platform SHALL reject all subsequent requests authenticated by any API_Key owned by that user with HTTP status 401 and a machine-readable error code `owner_disabled`.

### Requirement 9: Administrative Visibility and Compliance Touchpoints

**User Story:** As a platform administrator auditing API usage during a compliance review, I want consolidated views of active API keys, webhook subscriptions, and export jobs across all tenants, so that I can answer regulator questions without running ad hoc database queries.

#### Acceptance Criteria

1. WHEN a platform administrator with the `admin:read` scope requests the global API_Key inventory, THE Survey_Platform SHALL return the list of all non-revoked API_Keys with the same fields exposed to Owner_Users plus the Owner_User identifier and the total request count over the trailing 30-day window, returning an empty list when no non-revoked API_Keys exist.
2. WHEN a platform administrator with the `admin:read` scope requests the global Webhook_Subscription inventory, THE Survey_Platform SHALL return the list of all active subscriptions with the same fields exposed to Owner_Users plus the Owner_User identifier and the failure count over the trailing 30-day window, returning an empty list when no active subscriptions exist.
3. WHEN a platform administrator with the `admin:read` scope requests the global Export_Job inventory, THE Survey_Platform SHALL return all Export_Jobs created in the requested time range with their Owner_User identifier, survey identifier, format, status, and storage size.
4. WHEN a platform administrator with the `admin:write` scope revokes an API_Key on behalf of compliance, THE Survey_Platform SHALL apply the same effects as Owner_User revocation and SHALL append an Audit_Log entry that records the administrator identity in addition to the standard fields.
5. WHEN the Compliance_Module requests a compliance export covering this feature's audit events, THE Survey_Platform SHALL include API_Key lifecycle events, Webhook_Subscription configuration events, webhook delivery outcomes, Export_Job lifecycle events, and rate-limit rejection events from the Audit_Log within the requested time range.
